# 安全说明与已知残留风险

本文件记录 2026-07-29 审计（`docs/audit-2026-07-29/`）修复后**仍然存在**的已知风险，
以及为什么在当前使用场景下接受它们。发现新的风险时请追加到这里，不要删除历史条目。

## 已接受的残留风险

### R-01 打开文件时的路径竞态（TOCTOU）

- **状态**：已缩小影响面，**无法完全消除**；由仓库所有者于 2026-07-29 确认接受
- **位置**：`src/electron/main.ts`，`shellOpenPathApproved()` 中唯一的 `shell.openPath` 调用点

**成因**：Electron 的 `shell.openPath` 只接受**路径字符串**，不接受已经过校验的文件描述符。
应用会先读取文件头确认它确实是 PDF/OFD/图片/EML 等允许的文档类型，再把**路径**交给
操作系统打开。校验与操作系统真正解析该路径之间存在一个时间窗口。若攻击者能在这个
窗口内把该路径上的文件原子替换为一个 macOS 应用程序包，系统打开的就是被替换后的对象，
而应用程序包会被执行。

只要仍然按路径打开文件，这个竞态就存在——这不是本项目特有的缺陷，而是所有
路径式系统打开 API 的共同性质。

**已做的收敛**：

- `renderer` 传入的任意 `path` **一律只定位（reveal），不打开**
- 只有主进程自己签发的 `ext:` 句柄才允许打开文件；`location` 键只能打开目录
- 内容校验与替身检测在铸造打开令牌前**立即**重跑，把窗口压到最小
- 全文件只有一个 `shell.openPath` 调用点，且只接受策略令牌，无法传入原始路径

**为什么接受**：

1. 攻击者必须**已经能写入用户自己的归档目录**。具备该权限时，他可以直接替换发票文件、
   篡改台账、读取全部已归档发票——这些都比抢赢一次竞态更直接、更可靠。
2. 该路径**无法被远程触发**：邮件、发票链接、开票平台都到不了这里，必须是本机已在运行的代码。
3. 本应用为**本地单机使用**，不面向多用户或不可信输入共享的环境。

**若使用场景变化**（多用户机器、共享目录、需要更强隔离），彻底消除的方式是
**取消“打开文件”能力，只保留“在文件管理器中定位”**，由用户自己双击。
代价是多一次点击，收益是该类风险归零。

### R-02 `shell.showItemInFolder` 的结果不可观测

- **状态**：已改为如实表述，无需进一步处理

该 API 返回 `void`，应用无法确认文件管理器窗口是否真的弹出。因此所有相关文案改为
「已请求在文件管理器中显示…」并给出找不到窗口时的下一步，而不是断言「已显示」。

### R-03 正式 Release 发布的是未签名安装包

- **状态**：由仓库所有者于 2026-07-29 决定并接受

仓库未配置代码签名证书（`MACOS_CERTIFICATE_P12`、`WINDOWS_CERTIFICATE_PFX`、
Apple 公证凭据），因此 `release.yml` 的签名信任链闸门始终失败——v0.0.4 的正式发布
就是这样在 6 秒内失败的。所有者选择「先发未签名的正式版」，而不是等证书或只发预发布。

**采取的做法**（没有削弱任何签名闸门）：

- `release.yml` 的三层 fail-closed 校验**全部原样保留**；只把自动 tag 触发器注释掉，
  避免每打一个 vX.Y.Z 就产生一次注定失败的运行。证书配好后取消注释即可恢复。
- 未签名通道（`unsigned-prerelease.yml`）新增 `mark_prerelease` 输入。它**只**决定
  GitHub Release 条目的标签，不改变构建、命名和校验方式：
  产物仍走 development 通道、仍带 `-unsigned` 后缀、仍按 development 规则校验
  「诚实标注为未签名」。
- Release 标题固定含「未签名」，README 顶部加了醒目告警，并给出 SHA-256 自校验命令。

**残留风险**：用户拿到的安装包无法由系统验证来源与完整性，Gatekeeper / SmartScreen
的告警是真实信号。受管设备与公司电脑不应安装，应从源码构建。
配好证书后应立刻恢复签名通道，并同步更新 README 第二节。

## 已经不再是风险的项（便于回溯）

- 测试用 mock OCR 与故障注入钩子曾会被打进发布包，可写入伪造发票数据、截断任意文件。
  现要求「可证明的开发树」，打包产物中一律失效，`mockProvider` 也被排除在 `build.files` 外。
- `open-path` 的允许根曾可由 renderer 通过 `save-config` 间接改写，进而打开
  `~/Downloads` 下的可执行文件。现允许根由主进程从磁盘配置推导并在保存时校验，
  且只按内容放行文档类型，可执行文件与替身/快捷方式一律拒绝。
- 破坏性重置的授权曾只在 renderer。现由主进程原生确认 + 发送方校验 + 独占租约把关，
  删除前对目标与最近存在祖先做 realpath 包含校验。
